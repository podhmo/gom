## 各レーンの要点

### A — SC-2 `Scope` 脱出の静的検査

二本立てで E0419: (1) 型位置 — `Scope` はパラメータの葉か関数
引数側のみ可（結果型・フィールド・コンテナ禁止）。(2) 使用点 —
値レベルの脱出解析（fixpoint でパラメータの escape flag を推論 →
`Symbol.Escapes` → `.gomi` の `//gom:noescape` ディレクティブで
export、import 側も同じ判定）。Go 関数は常に逃げる扱いで、
`Scope.run` 系の本体引数だけ非脱出として配線。
[decision](../decisions/2026-11-22-scope-escape.md)。

### B — SC-3 ネイティブ `defer` lowering

scope ハンドルが登録引数以外で使われない body を検出して登録点を
`core.Defer` に書き換え、呼出し側を `f (rt.NewScope())` に変換。
`defer_err`/`on_err` がある `run_result` は named result + `errs`
fold。それ以外はランタイム scope のまま。
[decision](../decisions/2026-11-22-sc3-native-defer.md)。
レビューで sealed-AST 規約（`default:` だけでは exhaustive と
見なさず全バリアント列挙が要る）の違反を多数指摘され、部分
visitor の switch を全列挙に揃え直した（`7ecd355`）。

### C — `@method` で record が Go interface を実装

`@method fn (g: Greeter) string () -> String` が、ふつうの関数
`string_` と転送メソッド `func (g Greeter) String()` の二本立てで
emit される。record が `fmt.Stringer`/`error` 等に適合する。
`Unit` パラメータはメソッド側で落とす。E0420: レシーバは自
パッケージの record（`Ptr T` 可）・ジェネリック不可・`@extern`
併用不可・`Result` 返り不可。`.gomi` は `@method` 行を往復する。

Devin Review で潰した 4 件:

- `gom fmt` が `@method` を落とし receiver-first を壊していた
- メソッド集合がファイル内の後の位置でしか見えず、前の body の
  interface 代入が E0401 になった → `checkDecls` の prepass で
  全 `d.Method` を先行登録
- 捨てる bind `_` が wrapper の転送呼出しにそのまま流れていた
  → `names` map で fresh name を sig・call 間で共有
- `Ptr T` レシーバのメソッドが裸の `T` のメソッド集合に混入して
  いた → `GomMethod.PtrRecv` + `ptrGot` で Go の method set と
  同じ計算に

### D — `--strict` 設計調査

split 設計を採用: `//gom:allow CODE` ディレクティブ（relaxable
whitelist、初期は E0301 非網羅 match・E0302 到達不能 arm）+
`--strict`（警告をエラー化する終了フラグ）。severity 全面の
filtering は拒否。
[decision](../decisions/2026-11-22-strict-mode.md)。

### E — defined-type 境界ギャップ調査

pun・`with`・`.value`（defined type 上）、`.gomi` 往復、import
側の emit は全部仕様通り。匿名 record の spread 制約は nominal
record 規則の帰結で追加仕様は不要と確認。唯一の発見:
`Go.conv` が単一フィールド record ↔ 要素型の相互変換を拒否する
（Go では `int64(u)`/`UserId(7)` が合法）→ 台帳へ記録。
