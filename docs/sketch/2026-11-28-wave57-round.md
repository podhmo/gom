## 発見メモ

- typo candidate の kind は「存在する」ではなく参照位置で使えるかで決まる。constructor pattern fallback は expression walker 経由でも constructor context を保持する必要がある
- fixture update は wire JSON の exact bytesを対象にしないと Unicode escaping 差で path を取りこぼす。一方、文字列置換では machine-facing `data.file` まで削るため span shape を見る必要がある
- diagnostic dependency bytes は compile-time snapshot だが、寿命は renderer ではなく compile invocation が持つ。`gom run` のように成功時レポートがない経路では child 開始前が明示的な解放点
- 未 import stdlib module の exact `list` と typo `lst` は現行 JSON 上同じ `namespace: "module"`。exact match を import 忘れ、OSA 距離 1 を typo candidate として分ける
- `namespace: "module"` を持つ診断でも `notModule` は名前解決済みなので、module candidate の対象にできない

## pitfall 一般化

- **候補 source の所有権と lifetime を分ける**: candidate index は driver から注入し、diagnostic bytes cache は invocation が所有する。renderer や global map に寿命を持たせない
- **fixture の portability は escaping 後の wire formで検査する**: 内部表現の path 文字列と JSON string bytesは同じとは限らない
- **調査 lane の decision は emitter 経路まで限定する**: diagnostic data の namespace だけでは複数経路を取り込む。実装対象は発生元関数と意味状態まで書く
