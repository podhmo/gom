## 学び

- **member-call ゲートは生成順序に依存する**: `g.imports` ゲートの
  呼び出しは import decl が先にないと一度も発火しない — import-decl
  が top-decl で均等競合するためほぼ全ての import がファイル末尾に
  来ていた。prelude で先頭に積むのが探索を開く（`fmt.Println` も
  実は 0 発火だった）
- **生成器の coverage 拡張はハーネス側の解決器も揃える**:
  `import "list"` を生成可能にしても fuzz の compile 経路が
  goimport だけでは全て E0203 拒否 — specCompile/cmd/gom と同じ
  gomimport 配線に揃えた
- **文法の seq index は rep の内側で再帰する**: `source-file` の
  member 1（rep）と rep 内 seq の member 1（top-decl）は同じ
  `curRule`/`i` に見える — 位置ベースのフックは member の型
  （rep/ref）まで見ないと重複発火する
- **ラベル run は宣言順が型同一性**: `types.Equal` がラベルをソート
  して比較していたのは positional Go ABI と矛盾（`~a ~b` と `~b ~a`
  は別 ABI）。個別診断のパッチではなく Equal の order-sensitivity
  を直した
- **name-only directive は scanDirective で拾えない**: index 列挙を
  仮定したパーサなので `//gom:mutable`（index 無し）は専用スキャンが
  要る — decision に明記済み
- prompts 作成時の freshness check: lane E は wave32 実装済みで
  stale だった。prompts 化前に「実装が既にあるか」を確認する

## 実装で発見したずれ

- `scanDirective` が `/* */` コメント内の directive 行を拾っていた
  （lane D レビュー #158 で修正 — 行頭 `//gom:` のみ有効の規則に統一）
- `checkLambda` の residual ret 構築が consumed-set を見ていなかった
  （wparams の消費済みフラグがなく残余 wparam のみから ret を組み立て
  られていなかった — lane F で修正）
- `types.Equal`/`iface/hash.go` の labeled-run ソート比較が
  positional Go ABI と不整合（lane F で宣言順比較に統一）
