## wave の経過

wave51 で決めた型推論を先に実装し、その成果を使って DMMF example を再評価する形に進んだ。lane B は「checksum を書く」だけでは足りず、release artifact に toolchain package があるか、local replace 先が存在するか、失敗時に既存 module を汚さないかまで review で広がった。lane E は code table の変更に見えて、実際には parser recovery が checker 診断へ到達できるかが中心だった。lane D では新機能が DMMF の主経路に効く一方、generic higher-order pipe の中では record 推論がまだ弱いことが再確認できた。

## 発見メモ

- lane A の label lending は shared function type を mutate できない。spine copy と reified meta rollback を分ける必要があった
- lane B の `go mod download` 成功は module bytes の存在だけで、生成コードが import する package の解決を保証しない
- lane E の unknown attribute は引数 recovery を先に作ると `@method` 用の誤診へ落ちる。unknown 用に simple argument を消費する recovery が要った
- lane C の scanner は意味解析ではない。証明できるのは approved helper の direct argument までで、helper 自体の正しさは test design 側の責任である
- lane D の direct `Ok { ... }` は通るが、`Result.map` lambda 内の bare record literal は E0407 のまま。型名前置 literal は依然として実用の主経路である

## pitfall 一般化

- **推論用 view と最終 conformance を分ける**: positional lambda にだけ label を落として渡し、residual contract は落とさない。推論の便宜を意味変更へ広げない
- **module 解決は package 単位で検証する**: checksum や download 成功だけでは生成コードが build できるか分からない。実際に import する package を readonly mode で解決する
- **失敗時 rollback は到達経路を pin する**: 早期失敗でも通る regression test は rollback を証明しない。依存挿入後の validation failure まで進むことを assertion に入れる
- **production diagnostic は到達可能性で評価する**: code table にあるだけではユーザー診断にならない。parser が回復で捨てる構文は、checker の専用診断へ進める形を fixture にする
- **調査 lane は negative probe も残す**: 動く形だけでなく、まだ E0407 になる形と推奨代替を残すと次 wave の採否材料になる
