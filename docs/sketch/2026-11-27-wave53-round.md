## 発見メモ

- init rollback は「init が作った file」を存在ベースで消すと、validation 中に外部から作られた同名 file を巻き込みうる。rollback backup と non-overwrite の attribution を分ける必要がある
- dangling symlink は `os.Stat` では存在しないように見える。rollback 判定は `Lstat` ベースでないと symlink を誤って消す
- pipe 経路だけ producer-side boundary retry を許す必要があった。通常適用へ広げると関数値の戻り値にも同じ推論が漏れる
- producer result root が open meta の boundary では List/Go.Slice のどちらへ bind しても強すぎる。この場合は sibling parameter propagation 自体を止める方が安全である
- tuple 要素を callback result position へ含めないと `(x, { ... })` の先頭要素が `Go.Any` に pin されず、`Go.Any` 側の静的 pin が失われる

## pitfall 一般化

- **失敗時 atomicity は file attribution を先に決める**: 「失敗時に消す」と「既存 file を消さない」は同じ path で衝突する。backup 対象、作成追跡、externally-created file の保存を別々に fixture 化する
- **推論 hint は硬い期待と柔らかい pipe hint を分ける**: pipe の boundary retry は最終 result conversion を見越した柔らかい hint であり、通常適用の hard expectation へ混ぜない
- **speculative propagation は ambiguity で止める**: open meta へ片方の boundary spelling を bind すると、copy conversion で両方ありえた型を片側へ過剰決定する
- **診断 fixture 例はその診断へ到達する形にする**: undefined name など前段診断があると、型検査や label の検証にならない。例を短くしても self-contained にする
- **推論が強くなるほど provenance が重要になる**: mismatch の発生位置が callback や分岐の奥へ移ると、注釈位置を辿れない診断が増える。型推論拡張と診断 UX はセットで評価する
