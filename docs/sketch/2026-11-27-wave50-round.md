## wave の経過

lane A で診断 coverage の土台を先に置き、lane C はその分類を使いながら診断 wire を一般化した。lane D は実装へ入らず decision と現行 fixture に絞り、lane E で checker 中央の文脈推論を実装した。lane E は speculative propagation の境界が難しく、型引数 merge・curried tail・label introduction の 3 点でレビュー駆動の修正が入った。最終 review の meta leak は lane merge 後の follow-up へ分離し、#277 の merge と main CI success を確認した。

closeout の運用自体もこの wave で変えた。lane PR に締め処理を載せるのではなく、lane PR 群とは別の closeout PR を wave 完了の単位にする。podhmo は closeout PR の 1 つ手前までの lane PR を merge し、round の merge 状態と main CI はその後に最終化する。

## 発見メモ

- lane A の meta-test は「診断を固定する」ことが目的ではなく、explain/example/fixture の腐敗を検出する保険だった。既存の docs/table 一致テストだけでは example 実行や coverage 分類を見られない
- lane C は red-first 明文化前に実装へ入ったため、診断表示を変える lane では fixture/期待値を先に赤くする運用が必要だった
- lane E の label 伝播は checking・inference・lowering の境界をまたぐ。静的期待型の label は explicit labeled function に必要でも、borrowed label を inference variable の契約と混ぜると curried binding・conditional lowering・direct generic conformance が壊れる。wave50 では label を含む文脈型を propagation 対象外にした
- nested generic record では constructor 単位の一致だけでは不十分で、型引数ごとに「既に分かった部分」と「文脈で分かった部分」を merge する必要があった

## pitfall 一般化

- **scope 外は lane で台帳登録しないが、具体的に残す**: lane は実装と検証に集中し、scope 外は検証レポートへ書く。closeout が TODO/open-questions へ昇格する。但し書きだけでは管理したことにならない
- **仕様・実装・文書のずれは closeout に送らない**: implementation-gaps は発見時即時登録が正。残件作業の登録だけが closeout の仕事
- **診断の足場を変える lane は red-first**: lane A のような meta-test/fixture がある領域では、実装前に期待差分を足して red を確認し、実装で green にする
- **speculative context は式の契約にしない**: expected type は checking を助けるが、式自身が宣言していない label や型を inference variable へそのまま bind してはいけない。label introduction と inference の境界が設計できていない間は、label を含む文脈型を propagation 対象から外す
- **generic propagation は構造ごとに merge する**: open だから丸ごと置き換える/置き換えないの二値ではなく、constructor・型引数・関数 tail ごとに既知情報を保存する
