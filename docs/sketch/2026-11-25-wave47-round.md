## 発見メモ

- lane F では snapshot 本体より、outer `go test` の cache key に `.snap` baseline が入るかが再現性を左右した
- lane C では directive の正は「著者の主張」と「本体からの推論」に分かれる。extern は本体を見られないので、同じ package directory・同じ canonical signature のときだけ引き継ぐ境界が必要だった
- lane A では generated registration function が package-level variable を参照しない形にしないと、Go の初期化依存解析が無関係な初期化順序まで変える
- lane A では nested error の括弧が concrete error implementation の shape ではなく、statically error な operand かどうかで決まる
- lane D では `uint` 対応の見落としは算術本体ではなく周辺写像に出た: `goFuncGomView` の逆写像、type-erased `Go.Any` boxing、`gomOnly`、constant-fold width、generator の builtin namespace
- lane D では eval の integer を width-64 bit pattern だけでなく unsigned interpretation 付きで運ばないと、type-erased display と `Go.try_as` が compiled reflection とずれる

## pitfall 一般化

- **境界型を足すときは正写像だけでなく逆写像・動的表現・診断用 fold を同じ表で監査する**: import mapping を開くだけでは callback seed、any assertion、constant-fold、method raw signatureがずれる。`Int`/`Int64` の既存 split がある型は、その pair をなぞるのが最も漏れの少ない監査表になる
- **type erasure では「値のビット列」と「その解釈」は別情報**: reflection は uint64 kind を返すが、eval の `VInt` は int64 だった。display/equality/assertion を揃えるには符号解釈を値と一緒に運ぶ必要がある
- **interface width は表現が同じでも型綴りを残す意味がある**: `Uint` と `Uint64` は普通の値では同じ uint64 でも、raw `uint` と raw `uint64` を要求する method interface を区別する。root/nested で emit 規則が違うので、型等価だけで判断できない
- **extern の metadata 引き継ぎは positional claim の寿命を先に決める**: 同名だから残すのではなく、signature が変わったら index 付き directive は別の意味になる。再生成の carry は canonical signature 一致が条件
- **generated initialization hook は依存を持たない形にする**: package 初期化で必要な registration は、他の package-level variable へ依存しない関数呼び出しにしないと、Go の dependency analysis が利用者の初期化順序を変える
- **教材 dogfoodingは生成物だけでなく test cache の入力まで見る**: clean checkout でpassしても、baseline 編集が cached pass を引かないと regression test にならない
