# Verification report: typed-AST evaluator (P1-12)

- 日付: 2026-11-02
- 対象: [decision: eval-value-model](../decisions/2026-11-02-eval-value-model.md)

`internal/eval` and `internal/eval/eval_test.go` are the prototype for
the draft decision. This report records what was verified before
marking it.

## API

- `eval.Program(*check.File) Result` evaluates a whole typed file:
  `TypeDecl`/`FnDecl` registration at `New`, then top-level `LetDecl`s
  in order, each `TestDecl` body as a function boundary (an `Err`
  result fails with E9005), and `main ()` when declared.
- `eval.New(f)` returns an `Evaluator` with `Run`, `Expr`, `Apply`,
  `Env`, `Global` — `Env` is where the harness binds host functions
  (`NewHostFunc`) and stub module members before evaluating.
- `eval.Expr(env, x)` evaluates one standalone typed expression.
- `Result{Value, Diags}`: `Value` non-nil + no errors means success;
  everything else is diagnostics. `Value.String()` is the
  deterministic comparison format and `eval.Equal` structural
  equality.

## Verified semantics (table-driven tests on hand-built typed ASTs)

- Literals: int (`0x`, `_` separators), float, bool, string (all Gom
  escapes incl. `\u{...}` and `\${`), char, unit.
- Evaluation order, witnessed by a tracing host function: function
  expression before arguments; arguments in *source* order including
  labeled-argument reorder (`~b: x ~a: y` evaluates `x` first, binds
  to declared positions via `ArgToParam`); list/record elements
  left-to-right; match subject then only the taken arm; `x |> f`
  evaluates `x` first; `&&`/`||` short-circuit.
- Closures capture their defining environment; `CallUnknown` applies
  unknown function values; `CallPartial` returns a `VFunc` with bound
  slots (`<fn add/1>`); labeled partial application leaves exactly the
  remaining params; over-application keeps applying to the returned
  function; `>>`/`<<` compose; `f<|x`/`x|>f` are single-arg applies.
- `match`: ordered arms, literal/wild/var patterns, `CtorPat`
  (positional and `{ field = pat }` forms, `~label:` args via declared
  field order), tuple/record/list (incl. `..rest`) patterns, `|` or-
  patterns binding the winning alternative via a scratch env, `as`
  patterns, `if` guards, and E9002 on dispatch failure.
- ADTs: nullary and payload variants, field access by index and by
  name, constructors as function values, structural equality
  (`eval.Equal`), labeled payload slots rendering `~name: v`.
- Records: literal order, declared declaration order when the type is
  registered, `{ base with ... }` update keeping other fields.
- `try`/`Result`/`|?>`: `try` unwraps `Ok`, escapes to the innermost
  function boundary as the function's `Err` return (nested fns do not
  propagate), reports E9004 on non-Result or unbounded escapes; `|?>`
  unwraps Ok into the step, short-circuits Err with the
  `step: orig` GoError wrap (spec 9.2 items 3-4), and treats a
  non-Result first value as `Ok`-wrapped.
- Sugared forms: `StrInterp`, `ignore`, `for x in <list>`,
  `{ base with f = v }`.
- Whole file: recursive `FnDecl` (`fact`), `LetDecl`s in order, `main`
  invocation, `TestDecl` Err → E9005.
- Error paths, all as diagnostics: `todo ()` (E9003),
  `assert_eq` mismatch (E9003), int `/` and `%` by zero (E9003),
  applied non-function (E9004), unbound symbol (E9004), unbound Go
  call (E9001), `go`/`select`/`Go.conv`/non-List `for`/misplaced
  holes and spreads (E9001/E9004), escaped `try` with no boundary
  (E9004).
- Go interop stubs: `CallGo` to a bound `NewHostFunc`, including the
  cute `f(_, arg)` partial call returning a one-param function that
  captures the evaluated args.

## Skipped (reported, not implemented)

`go` expressions, `select`, `for` over non-List iterables, `import go`
calls without a harness stub, `Go.conv` ascriptions, Ref/Array/Ptr/
Chan/Task values, Go methods, and real Go interop — all E9001
diagnostics in P1 scope.

## Divergences found

- `|?>` nameless-step position renders `file:byteOffset`, not the
  spec's `file:line` — [problem](../problems/2026-11-02-eval-pipe-try-step-name.md).
- (Correction after review) the `|?>` description above was written
  against the buggy first implementation. The fixed semantics: an
  incoming `Err` passes through untouched without evaluating the step;
  the `step: orig` wrap applies only to an `Err` *produced* by that
  step, keyed on the pipe node's own `Result _ GoError` type.
- The evaluator assumes undocumented check-side contracts (Lit.Text
  lexeme form, irrefutable-pattern trust, Result nominal detection,
  `main` found by name) — [problem](../problems/2026-11-02-eval-typed-ast-contract.md).
- Int32/Int64 literals share the 64-bit `VInt`; width-truncation
  semantics are not modeled (P1 is monomorphic — noted for B-4).
- `StrText` parts are unescaped by the evaluator; if check stores
  decoded text the behavior diverges (same contract problem above).

## Harness notes for the comparison runner

- Inject Go stubs via `env.Bind(goSym, eval.NewHostFunc(name, arity,
  fn))`; `CallGo`/`CallDirect` both reach it, and errors returned by
  the stub become E9003 panics.
- Expected-value comparisons: `Value.String()` for rendering,
  `eval.Equal` for structure; diagnostics compare by `Code`+`Message`
  +`Data`.
- `Evaluator.Apply(v, args...)` applies runtime values curried —
  useful for asserting on partial-application results.
