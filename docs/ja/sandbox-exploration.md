# sandbox 探索プロセス

「gom で普段使いのツールを書き、観測から不足機能を TODO まで繋げる」
探索の回し方。初回は PR #163（log・ideas・プロンプトの `.md` は
[docs/sketch/ja/](../sketch/ja/) の `2026-11-23-sandbox-explorer-*.md`
に転記済み、コードは未マージ PR 側に残る）。

この文書はプロンプトの canonical な置き場所。**メンテ対象の文書** —
運用が変わったらこちらを更新する。各 run が残すプロンプト
（`docs/sketch/ja/2026-11-23-sandbox-explorer-prompt.md` など）は
その時点のスナップショットなので、改訂はこの文書側だけで行う。

## 運用モデル

- `sandbox/` は常に空の状態から探索を始める作業場。run ごとの
  サブディレクトリは切らない（前回分は残らないため）。
- run の成果物は PR にして**マージしない** — PR がそのまま
  アーカイブになる（リンクは残る）。
- 保存価値のある `.md`（log・ideas・プロンプト等）は棚卸し時に
  `docs/sketch/ja/YYYY-MM-DD-<slug>.md` としてリポジトリへ転記する。
  `.gom` のコードは転記せず PR 側に残す。

## 陳腐化を避ける方針

プロンプト本文に「既知の罠」「不足機能一覧」「実装済み機能」の
**具体的な中身を埋め込まない**。機能が増えるたびに腐るため。代わりに
実行時に以下の生きた情報源から拾わせる:

- `gom-agent-guide` スキル — `.gom` の書き方・ありがちな間違い・
  ツールチェーンの使い方
- `docs/sketch/ja/` の最新 sandbox アーカイブ — 直近 run の
  「領域地図」「既知の罠」「諦めたもの」
- `docs/implementation-gaps.md` の未解消項目
  （`rg '^- \[ \]' docs/implementation-gaps.md`）
- `TODO.md` の未完了タスクと `docs/open-questions.md`
- [sandbox-attempts.md](sandbox-attempts.md)（過去 run の試作一覧）
  — 題材の重複回避。タイトル（1 行説明）だけを見る。アーカイブ
  本文は探索後の再検証フェーズで読む（先に読むと前回の結論に
  引っ張られる不具合が run 2 で発生した）

プロンプトを使う人が行うのは変数の穴埋め（`{前回のrun名}` など）だけ
に留める。

## フェーズ構成

1. **探索フェーズ**（プロンプト A）: ツールを書いてログを取る
2. **棚卸しフェーズ**（プロンプト B）: ログから不足機能を整理して
   tracker に反映し、保存する `.md` を `docs/sketch/ja/` に転記する

## プロンプト A（探索者）

`---` の内側をそのままセッションの最初の指示として使う。
`{前回のrun名}` はその時点の `docs/sketch/ja/` のアーカイブを見て
埋める。

---

あなたは探索者です。gom で実用的なコードを書き、得意領域・不得意領域・
明らかに無理な危険領域を観測・記録してください。

## 作業場所とコミット

- `sandbox/` ディレクトリで作業する。空の状態から始まる。
- 最初に `sandbox/.gitignore` に `*.go` と書く — 生成される `.go`
  ファイルはコミットしない（`go vet` / staticcheck が生成コードを
  検査するため）。
- コミットは好きなタイミングで。最終的に PR を作るが**マージしない**
  — PR がそのままアーカイブになる。
- `sandbox/` に置いた `.md` は棚卸しで `docs/sketch/ja/` に転記される。

## 読むもの・読まないもの（順序が大事）

先に前回の探索結果を読むと、その結論に引っ張られてアイデアと
観測が浅くなる不具合があった（run 2）。読む順序を固定する:

- **アイデアメモを書く前に読んでよいのは試作一覧だけ** —
  `docs/ja/sandbox-attempts.md` のタイトルと 1 行説明（結果欄は
  再検証フェーズまで見ない）。
  過去 run の log・ideas・領域地図のアーカイブ本文は読まない。
- **アイデアメモのあと、実装の前** — `gom-agent-guide` スキル
  （OCaml/F#/Go の習慣で書くと構文を間違える）、
  `docs/implementation-gaps.md` の未解消項目、`TODO.md`。
  直近で増えた機能と「今回再確認しなくてよい罠」を要約する。
- **探索が終わったあと（再検証フェーズ）で初めて** —
  `docs/sketch/ja/` の最新 sandbox アーカイブ（{前回のrun名}）
  と過去 run の ideas メモを読む。ここで読む目的は重複指摘の
  照合であり、探索範囲の入力ではない。

## 手順

1. **アイデアメモ**: gom のことは考えず、「Go で普段作るカジュアルな
   ツール」を何個か `sandbox/ideas.md` にメモする。重複回避には
   `docs/ja/sandbox-attempts.md` の
   タイトルと説明だけを見る（結果欄は再検証フェーズまで見ない）—
   アーカイブ本文を読んでから書かない。
2. **実装と検証**: 各ツールは `gom check -format text` →
   `gom run FILE -- args` で実動作確認（実在コマンドとの比較が理想:
   wc・sha256sum・curl 等）。
3. **ストリーミング記録**: 発生したエラー・不足機能・迂回・諦めを
   雑でいいので `sandbox/log.md` に時系列で追記していく。後で清書
   しない。素のまま残す。
4. **諦めの保全**: 数回試行錯誤して無理なら諦める。そのときの状況と
   コードを「第二の財産」として残す（動かないコードもファイルとして
   残す）。
5. **再検証**: ここで初めて前回アーカイブ（{前回のrun名}）を読み、
   「解消済みか検証したい項目」を `sandbox/recheck/` の最小 probe で
   確認して `sandbox/recheck.md` に残す（結果だけでなく probe の
   コードも残す）。試作一覧の結果欄もこの段階で見てよい — 過去の
   `断念`・`一部断念` は再検証の候補、`成功` が多い領域は次回の
   題材から外す材料にする。
6. **領域地図**: 最後に得意/不得意/危険の3分類でまとめ、log.md に
   書く。前回の領域地図があれば追認・修正・新発見の形にする。

## 記録してほしいもの

- すんなり書けたもの（成功記録 = 第一の財産）
- エラーメッセージと解決法（E0101, E0401 等のコード付きで）
- 迂回したもの・回復不能だったもの・諦めたもの（状況とコード）
- sum types / pattern match がうまくはまった場面
- 「仕様・実装・文書のずれ」に見えたもの → `docs/implementation-gaps.md`
  にも登録

## 探索テーマのヒント（毎回違う角度から）

テキスト処理 / CSV・JSON / 日時 / ファイルシステム / ネットワーク /
並行・並列 / プロセス起動 / HTTP サーバ・クライアント / テンプレート /
正規表現 / CLI flag / 文字エンコーディング / シグナル・タイマー /
データ構造の再実装 / Go の標準ライブラリの薄い API を gom で包む、等。

## プロンプト B（棚卸し）

探索 run の PR ができたら、成果を tracker に反映するためのプロンプト。
`{対象のPR}` を埋めて使う。単発セッションでよい。

---

{対象のPR} の sandbox 探索の成果を棚卸しして、保存する文書を
`docs/sketch/ja/` に転記し、gom の不足機能・不具合を tracker に反映
してください。

## 手順

1. 対象 PR のブランチから保存する `.md` を取り出し、
   `docs/sketch/ja/YYYY-MM-DD-<slug>.md` として転記する
   （先頭に転記元と run 名を 1 行添える。`.gom` のコードは転記せず
   PR 側に残す）。観測の原本である log は必ず転記する。
   転記に伴い、対象 PR 内の tracker 追記（open-questions や
   implementation-gaps へのリンクが `sandbox/*.md` を指しているもの）
   は転記後の `docs/sketch/ja/` のファイルを指すように直す。
2. 転記した log を読み、「不得意」「危険」「諦めたもの」から
   不足機能・不具合・静かな罠を抽出する。各項目に再現コード・
   回避策・影響する Go 慣用句を添える。
3. `docs/sketch/YYYY-MM-DD-<slug>.md` に整理メモを書く
   （書式は `docs/sketch/README.md` — 先頭に「目的」「関連」）。
   各項目の対応先をメモ内で明示し、根拠は転記済みのアーカイブと
   対象 PR にリンクする。
4. 各項目を既存 tracker と照合して振り分ける:
   - 「仕様・実装・文書のずれ」→ `docs/implementation-gaps.md` に登録
   - 設計が未決のもの → `docs/open-questions.md`
   - 決まっていて手を動かすだけ・明らかなバグ → `TODO.md`
     （`.claude/skills/todo-md` の規則に従う）
   - 既に tracker があるもの（`rg` で problems/decisions/spec を検索）
     → 新規項目を作らず既存項目へ追記
   - 仕様済みの設計・回避口が文書化済みのもの → tracker に載せず
     メモで根拠を示す
5. `docs/ja/sandbox-attempts.md` に、今回の run の試作したものの
   タイトル（1 行説明）と結果の 1 語分類（`成功`/`一部迂回`/
   `一部断念`/`断念`/`未検証`）を追加する。本文へのリンクは張らない。
   過去 run の項目は recheck の結果で結果欄を更新する（失敗しても
   後で成功したら `成功` に直す）。
6. 変更を PR にする。生成物が docs のみなら Go の検証は不要。

## 注意

- log の記述は素の観測なので、仕様で禁止済みの挙動と本当の不足を
  取り違えないこと（spec.md と decisions/ を確認する）。
- 勝手に spec を書き換えない。ずれは台帳へ。
- TODO には「decision を起こしてから実装」を含めてよいが、要不要が
  未決の純粋な設計問いは open-questions へ。
