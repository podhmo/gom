Gomトランスパイラーの実装 — ASTからGoソースまで

調査日: 2026-11-20。対象: podhmo/gom、main のコミット e14baa034cf716ec6f1964ce6d1f481535a77722。本書はGo/Python/TypeScriptを使用できる読者に向けた、実装のコード読解資料である。プログラミング言語処理系の用語は必要に応じて定義する。Go/Python/TypeScriptにたとえる比喩は用いない。

現行実装を説明する文書であって、言語仕様の規範ではない。言語として保証することは docs/spec.md、設計意図は docs/design.md、実装選択の経緯は docs/decisions が正となる。例示する「概念的なIR」「概念的なGo」は実際のダンプをそのまま写したものではない。

1. AST生成後のコンパイラ全体像

Gomは式指向、静的型付けの言語である。型推論、代数的データ型（ADT）、パターン照合、関数の部分適用、Goパッケージ呼び出しを持つ。パーサーが生成した構文木をすぐにGoの構文へ置換するわけではない。後続フェーズは意味を一つずつ決定し、最後のコード生成には未解決の意味判断を持ち込まない。

Gomソース .gom / インターフェース .gomi
  │ syntax: 字句解析・構文解析
  ▼
表層 AST  (*syntax.File)
  │ resolve: 名前解決・import・Symbolへの束縛
  ▼
Resolved  (表層AST + Defs/Usesなどの対応表)
  │ check: 型検査・制約解決・関数呼び出し分類
  ▼
型付き AST  (*check.File)
  │ pattern: パターンの網羅性・冗長性検査
  ▼
検査済み型付き AST （新しい中間表現は作らない）
  │ lower: ANF化、match決定木、部分適用・脱出・Go変換
  ▼
Core IR  (*core.File)
  │ core.Validate、初期化循環、@tailrecの検査
  ▼
codegen: 宛先指定によるGoコード出力
  │ Goの式・型の一部にgo/astとgo/printerを使用
  ▼
Goソース文字列 → go/format → //lineとSourceMap
  ▼
.go / _test.go → Goツールチェーン
段階 入力 生成物または結果 主な責任

check Resolved check.File 各式の型、関数適用の規約、型引数を決定する
pattern check.File 診断 matchの網羅性・冗長性を判定する

このフェーズの順序は internal/build/build.go の Compile が示している。エラーがあれば次の意味解析フェーズへ進まない。.gomiは型検査までで止まり、gom checkはパターン検査までで止まる。ソースコード生成の成功と生成後のGoコンパイラでの成功は別段階である。

設計境界として最も重要なのは、codegenにGomの意味を再判断させないことである。たとえば関数が既知か、適用が飽和しているか、Goとの変換が要るかという判断は型検査・loweringで決定済みの情報を受け取る。

2. コンパイル単位: ファイルとパッケージを区別する

同一ディレクトリの.gomはひとつのパッケージを構成する。別ファイルにある宣言を参照できるので、ファイル単位で名前解決・型検査を独立して完了させると前方参照が壊れる。

build.CompileFilesは先に全ソースを構文解析する。次にresolve.Filesがパッケージ共通スコープで名前を集め、check.Filesがファイルをまたぐ宣言集合を型検査する。結果は各ファイルのcheck.Fileへ分配する。その後は兄弟ファイルの宣言をpattern.Options.Decls、lower.Env.Siblingsに渡してファイルごとに処理する。初期化循環・相互再帰は再びパッケージ単位で検査する。

つまり次の二種類の集約がある。

  • 名前・型の解析では、複数ファイルにまたがる定義の同一性を共有する。
  • Core生成とGo出力では各ファイルの成果物を維持し、ファイル横断的な性質だけを後で集約して調べる。

importはファイルローカルであり、トップレベル宣言はパッケージで共有する。この区別はresolve.Filesのスコープ構築で実装されている。

CompileFilesの現行コードはファイルごとのGoコードを先に生成し、その後でパッケージ単位のCore検査を実施する。検査でエラーがあれば全ファイルのOutputを破棄するので、完成物は部分的には返らない。ただし不要なコード生成が起きる余地がある。後述の調査記録に改善候補として記載した。

参照: build.go、check/files.go。

3. 名前解決 — 識別子の綴りから宣言オブジェクトへ

3.1 なぜ必要か

パーサーが生成したsyntax.Identは識別子の綴り・位置を持つが、それだけではxがどの宣言か分からない。同名のローカル束縛、パターン変数、トップレベル関数、型コンストラクタ、外部パッケージのメンバーを区別する必要がある。以後の型検査・置換・コード出力が、その識別子の同一性に依存する。

resolve.Resolvedは表層ASTを保持し、Defs map[*syntax.Ident]*SymbolおよびUses map[*syntax.Ident]*Symbolなどの対応表を持つ。Defsは定義を導入する位置、Usesは参照である。対応する*resolve.Symbolが同じであることが、綴りの一致より強い意味を持つ。

3.2 スコープとは

スコープは、ある位置で参照可能な名前を宣言へ対応させる環境である。実装は項（term/value）と型（type）の名前空間を区別し、親スコープをたどって探索する。パッケージのトップレベルスコープと、ファイルのimportスコープ、式や関数の局所スコープは役割が異なる。シャドウイングした同名の変数は、それぞれ異なるSymbolを指す。

3.3 複数パスで収集してから本体を読む

resolve.Filesは、各ファイルでcollectし、全ファイルでbindTermsし、最後に本体をresolveDeclsする。外部宣言、型、コンストラクタなどを先に集めた後にトップレベルの項を束縛し、それから式やパターンの識別子を解決する。

これにより、後に宣言した関数や別ファイルの名前が参照できる。反対に、同じスコープへの重複定義を検出できる。名前を見つけることと、その名前の型・実行規約を決めることは別処理である。

3.4 型検査へ保留する参照

x.MのMが何かはxの型が分からなければ判定できない場合がある。レコードのフィールド、Goメソッド、Gom側のメンバーなどは型依存である。すべての識別子を名前解決だけで強制的に確定するわけではない。checkが受け手の型を解いた後に確定する部分を残す。

3.5 外部宣言のロード

import "path"ではinternal/gomimportが.gomiインターフェースを読み込み、公開面の型・メンバー・コンストラクタを提供する。Goのimport goではinternal/goimportがgo list -export、Goの型情報（go/types）を利用する。ローダーは複数利用者に対して同じセッション内のシンボルを共有し、型同一性を保つ。外部の名前を毎回文字列から再構築する方式ではない。

参照: resolve/resolve.go、resolve/scope.go、gomimport/loader.go、goimport/loader.go。

4. 型推論 — 型の未知数を解く

4.1 型表現を理解する

internal/typesは、名付き型Con、剛性型変数Var、推論用のメタ変数Meta、関数Func、タプルTuple、Go由来の型Goなどを持つ。剛性型変数aは多相シグネチャに現れ、ある使用箇所で恣意的にIntへ固定しない。メタ変数?mは未解決の未知型であり、制約からIntなどへ束縛できる。types.Chaseは既に束縛されたメタ変数を追って具体型を取り出す。

例: 多相な同一性関数を二回呼ぶ場合、第一の使用箇所ではaを?m1へ、第二では独立した?m2へ置換する。これがインスタンス化（instantiation）であり、それぞれIntとStringに解決できる。

4.2 単一化（unification）

単一化は、二つの型が等しくなるようなメタ変数への代入を計算する操作である。unify(want, got)は期待型と実際の型を受け取る。未知型なら束縛し、複合型なら型コンストラクタとその引数を再帰的に比較する。

want: List ?a
 got: List Int
------------------
? a := Int     （概念図）

?a = List ?aという代入は無限型を要求する。occursは未知型が代入先の内部に現れるか検査し、自己包含を拒否する。これをoccurs checkと呼ぶ。Gomにはさらに数値、整数、順序、等価性などの制約フラグがあり、メタ変数が具体化した時点で検証する。

Go.Anyは値位置ではボックス化の受け皿になる。しかしOption Go.Anyという型の引数位置ではOption Intを同じ型として扱わない。これらを区別するためunify（値スロット）とunifySub（複合型の内部）の規則が分かれている。

4.3 Hindley–Milner型推論の構成要素

Hindley–Milner（HM）型推論には、型の制約を解く単一化のほか、let束縛での型一般化（generalization）と、参照時の具体化（instantiation）がある。一般化は、環境と共有されていない未解決の型変数を∀aのような多相型へ変える。参照時は型変数ごとに新しいメタ変数を生成する。

let id = fn x -> x
  推論型: ?a -> ?a
  一般化: forall a. a -> a

id 10    : a -> a を ?u -> ?u に具体化、?u = Int
id "foo" : a -> a を ?v -> ?v に具体化、?v = String

ただしGomの実装は教科書のAlgorithm Wをそのまま走らせるわけではない。明示的アノテーション、期待型の伝播、Go型との適合、遅延される選択・適用、複数回の制約処理が加わる。

4.4 Value restriction（値制限）

一般化を無条件に許すと、型変数を含んだ計算結果が可変状態などを通じて共有され、使用箇所ごとに別の具体型を想定することが問題になり得る。GomのcheckLetDeclは、主にトップレベルのletで右辺が構文的な値（ラムダ、リテラル、値のみで作った集約など）かを検査し、一般化を制限する。通常の関数呼び出しの結果は構文的な値ではない。ローカルletが自由に多相化される設計ではない。

既に前方参照や再帰的参照で単相の形が使われた束縛は、一般化によって先の参照と食い違わないように制限する。トップレベルのletがラムダを保持すると、FnDeclへ再分類してGoの関数宣言を生成することもある。これには初期化依存グラフを不正に循環させない効果がある。

4.5 双方向の型付け（bidirectional typing）

式から型を合成する方向だけでなく、周囲が要求する型を式へ渡す方向もある。checkExpr(e, want)は必要に応じて期待型wantを子の式へ伝える。ラムダの引数や空のコレクションなど、自身だけでは型を決めにくい式は、期待型があると確定できる。

型の誤りはcheckで診断される。エラーが起きても診断を集めるため部分的な型付きASTを返す場合があるが、それをlowerへ渡してはならない。

4.6 型の最終確定は固定点反復

check.finalizeは保留案件を一回だけ再訪するのではない。revisitSelects、replayResolvedApplies、フィールド代入や反復可能な型の保留処理を繰り返し、解決が進まなくなった場合にデフォルトの型を適用する。新しく解けた型が、別のメンバー参照を解決し、さらにその呼び出しが別の型変数を解くためである。

この「新たな情報が得られなくなるまで繰り返す」操作を固定点反復（fixed-point iteration）という。デフォルトの数値型を早く適用すると、本来は周囲のInt64などから決まるはずのメタ変数を誤って固定する可能性がある。最後に型リテラル範囲、変換、未解決変数なども検査する。

参照: check/check.go、check/unify.go、check/expr.go。

5. 関数適用の規約を型付きASTで固定する

5.1 呼び出しの分類

f a bという構文だけでGo出力は決まらない。fが既知のGom関数か、未知の関数値か、Go関数・メソッドか、指定された引数数が足りるかによって実装が異なる。

check.ApplyはCallInfoを持つ。KindはCallDirect（既知Gom関数の飽和呼び出し）、CallPartial（既知Gom関数の部分適用）、CallUnknown（関数値）、CallGo（Go関数規約）を区別する。Callee、TypeArgs、Arity、FlatArity、Applied、Unapplied、ArgToParam、HoleIndex、Variadicなども記録する。

Arityは宣言上の引数数であり、FlatArityは戻り値がさらに関数である場合の引数列まで平坦化した数である。ラベル付き引数が返された関数のパラメータを指定することもあるため、この違いは必要になる。

5.2 実引数の評価順と引数配置は別

ArgToParam[i]は「ソース上のi番目の実引数が宣言側の何番目の引数を埋めるか」の対応を表す。ラベル引数を宣言順に並べ替えるときも、副作用を持つ実引数の評価順序はソース順に維持しなければならない。loweringは一度ソース順で値を束縛した後、呼び出しの引数スロットへ配置する。

5.3 メンバー選択が未確定なら呼び出しも保留

x.Mでxの型がまだメタ変数なら、MがGoメソッドかGomメンバーか判定できない。checkはpendingSelsとpendingAppliesを用いて選択と適用を保留する。受け手型が確定したらreplayGoApplyまたはreplayGomApplyで引数規約を検査し直す。CallInfoはこの最終処理で確定され、lowerでは名前の綴りやASTの形から判断をやり直さない。

参照: check/call.go、check/apply.go。

6. パターン検査: 網羅性と冗長性の証明

6.1 これは実行用の決定木生成ではない

型付きASTのmatchに対しinternal/patternが行うのは、全値がいずれかの腕に一致するかという網羅性（exhaustiveness）と、到達不能な腕がないかという冗長性（redundancy）の検査である。ここでは新しいCore IRを作らず、診断を出す。実際に分岐して値を計算するための決定木は後段のlower/pat.goが生成する。

6.2 パターン行列（pattern matrix）

実装はLuc Marangetの Warnings for pattern matching（JFP, 2007）に基づく。パターン行列Pは既に登場したパターン列を行として保持する。新しい候補パターン列qが、Pにまだ覆われていない値を一つでも受理するなら、qは有用（useful）である。

形式的にはU(P,q)を「qに一致し、Pのいずれの行にも一致しない値が存在する」という命題として考える。U(P,q)=falseなら候補の腕が既存の腕によって覆われ、到達不能と判断できる。

Shape = Circle(Float) | Rect(Float, Float)
P = [Circle _]
q = [Rect _ _]
U(P,q) = true

P = [Circle _, Rect _ _]
q = [_]
U(P,q) = false

6.3 specialize と defaultMatrix

specialize(P,C)は先頭のパターンがコンストラクタCに一致する行を取り、そのペイロードの各フィールドへ列を展開する。先頭がワイルドカードの行もCの引数数だけワイルドカードに展開される。他のコンストラクタの行は除外する。これによって入れ子の照合問題を再帰的に扱える。

defaultMatrix(P)は先頭がワイルドカードの行だけを残し、その先頭列を落とす。先頭列に現れたコンストラクタ集合が型の全候補を覆わないとき、列挙されていない値を扱う可能性はワイルドカード行によって判定する。

usefulは候補がコンストラクタで始まればspecializeし、ワイルドカードなら既出のコンストラクタ集合が完全なときに各コンストラクタへ分岐、不完全ならdefaultへ進む。再帰型のワイルドカードを無限展開しないためにも、この分岐が必要になる。

6.4 反例の生成とguard

missingは未被覆のパターンを構築する。コンストラクタの宣言順と深さ優先で決定的に反例を生成し、診断E0301のmissing_patternsに格納する。腕の到達不能はE0302である。orパターンは代替を展開する。

guard付きの腕は、guardの条件が偽になり得るため網羅性を保証しない。したがって網羅性行列には無条件の腕のみを投入する。引数やletのような反駁不能（irrefutable）パターンが求められる位置も別途検査される。

参照: pattern/matrix.go、pattern/cell.go、pattern/check.go。

7. Core IRとANF: 構文上の複雑さを減らす

7.1 Core IRが表す契約

中間表現（Intermediate Representation, IR）とは、ある処理段階が次段階へ引き渡すプログラムの構造化表現である。CoreはGo出力に必要な意味を明示し、表層の糖衣構文を消したIRである。

core.Exprは、副作用を生まず安価に参照できるAtomと、Let.XやBody.Tailに配置する複合式の二種類に大きく分かれる。core.Bodyは順番のあるLetsと結果となるTailを持つ。Coreには元のパターンや_プレースホルダやパイプ演算子は残らず、それに相当するDSwitch、Closure、Conv、EscapeResultなどの具体的ノードを持つ。

7.2 A-normal form（ANF）

A-normal formは、複合式の評価を一時変数へ分離し、各演算の入力を単純なオペランドへ揃える表現である。Gomでは厳密な純粋ANFというよりANF風の順序付き束縛を採用する。

入力の概念例:
  f (g ()) (h ())

Coreの概念例:
  let t1 = g()
  let t2 = h()
  tail = f(t1, t2)

これらの一時変数は単なる最適化ではなく評価順序の意味を保持する。g()とh()に副作用があるとき、引数を宣言順へ並べ替える前にソース順で評価する必要がある。lower/expr.goのseq.emitは順序付きのLetを追加し、atom/asAtomは複合式を必要に応じて一時束縛へする。exprBodyはLetの列と末尾式を組み立てる。

ブロックの途中の式はその値を捨てても、作用のある計算を実行する必要がある。stmtとblockExprがこの扱いを担う。

7.3 不変条件（invariant）

不変条件とは、そのフェーズの成果物が必ず満たすと次段階が仮定してよい性質である。Coreには、オペランドが単純なこと、複合評価の順序が確定していること、型とソース位置を保持すること、適用規約・引数配置・型変換・脱出先が確定済みであること、パターンが残っていないことなどの条件がある。

lower.Fileは構築したCoreをcore.Validateへ渡し、codegen.Fileもコード出力の前にCoreを検証する。後段で意味判断を再発明せず、入力の契約が壊れれば失敗とする設計である。

参照: core/expr.go、core/node.go、core/validate.go、lower/expr.go。

8. パターンを実行用の決定木に変換する

lower/pat.goは「未処理の照合義務」のキューを持つarmStateを処理する。各義務は「この対象AtomがこのPatternと一致するか」という組である。armStateには照合待ちのtodo、一致の途中で得たbinds、腕本体の情報などがある。

  1. 先頭の腕に照合義務が残っていなければ、その腕を実行する葉を作る。guardがあれば条件分岐する。
  2. 変数、ワイルドカード、タプル・レコードの分解など、失敗しないパターンは部分対象への義務を追加する。
  3. orパターンは状態を各代替に複製する。
  4. コンストラクタ、リテラル、リスト形状など、値の判定が必要なパターンが来たら、その判定による分岐を構成し、各枝で残った腕群を再帰的に処理する。

Coreの決定木はDLeaf、DGuard、DSwitch、DPanicなどのノードを用いる。DSwitch.KindにはSwitchType（ADTの型）、SwitchTag（Result等のタグ）、SwitchValue（値）、SwitchList（リスト形状）がある。

概念的な決定木:
  switch Shape のコンストラクタ
    Circle → payloadを取り出す → 円の計算
    Rect   → payloadを取り出す → 矩形の計算
    default → invalid-variant panic

静的検査が網羅性を証明していても、Go側の不正な値やゼロ値の侵入を考慮してDPanicを残す。パターン変数を分岐の複数箇所へ展開しても束縛が衝突しないよう、Symbolの置換も行う。

「網羅性を判定するパターン行列」と「実行分岐を組み立てる義務キュー」は目的も出力も異なる。前者は診断を出し、後者はGoに変換できる決定木を作る。

参照: lower/pat.go、core/tree.go。

9. 部分適用、カリー化、関数値の表現

9.1 CallInfoをCoreのノードへ写す

lower.applyCallは型検査が確定したCallInfo.Kindを受け、directCall、partialCall、unknownCall、goCallへ分岐する。

CallKind Coreの主な表現 意味
CallDirect CallDirect 既知のGom宣言の飽和呼び出し
CallPartial Closureの列 不足引数を受け取る関数を生成し、その中で飽和させる
CallUnknown CallFunc 実行時の関数値へ引数を適用する
CallGo CallGo Goの引数規約に従い呼ぶ

過剰適用はまず既知の宣言を飽和させ、その戻り値の関数へ残りの引数を適用する。部分適用の場合、中途半端なCallDirectを残さず、未適用の引数を受け取るClosureの連鎖を組み立てる。

9.2 canonical関数値と宣言のarity

Gomの関数値の標準的な表現は、引数1つにつきGo関数を1つ持つカリー化表現である。たとえばA -> B -> Rは概念的にfunc(A) func(B) Rとなる。他方でトップレベルのfn f a b宣言はGoのfunc f(a A,b B) Rに対応する。多引数宣言を「関数値」として渡すときは、必要に応じてカリー化アダプタを作る。

9.3 高階関数引数のflat表現

現行実装には、高階関数の宣言された複数引数の関数型パラメータを、flatなGo関数型へ適合させる規則がある。lower/flat.goのUncurry、curryEta、CallFunc.FlatArityなどが、canonicalな値とflatなパラメータを区別する。繰り返し使われるコールバックがfunc(A,B)Rなら、各呼び出しでの中間クロージャの生成を減らせる。

重要なのは最適化だけでなく、部分適用によって副作用がいつ実行されるかという意味である。呼び出しの平坦化は型だけでなく適用タイミングに関係するため、Coreで規約を確定させる。

参照: lower/expr.go、lower/flat.go、core/call.go。

10. Go相互運用: 型と呼び出し規約の橋渡し

Goの関数は、カリー化、エラー表現、スライス、any、named type、複数戻り値などに関してGomと異なる。goimportはGoの元シグネチャを読み、checkにはGom側から見た型を、lowerには元のGo呼び出しを実装するための情報（GoSig）を提供する。

core.GoResultsは戻り値の形を区別する。戻り値がない場合、単一値、errorだけ、(T,error)、ペア、一般の複数戻り値、末尾errorを持つ多値などである。ResultFromGo、OptionFromGo、TupleFromGo、ErrorFromGo、EscapeCallといったノードに分ける。

Goの戻り値 必要な意味変換
0個 効果として呼び、GomのUnitを得る
1個 必要なら型変換する
(T,error) Resultに組み立てる、または脱出条件へ融合する
(T,bool)等 ペアの意味に従ってタプルやOptionを形成する
3個以上 要素をタプル化し、末尾errorを必要に応じてResult化する

ListとGoのスライスを結ぶ際にはコピーが必要な場合がある。anyへのボックス化、Goのinterfaceへの適合、nilの可否、数値変換も同じ境界で決定する。Goの戻り値が「二つ」というだけでResultにしてはいけない。正しい分類には元のGo型とGomで利用するときの型の両方が必要である。

参照: goimport/mapping.go、lower/expr.go、core/call.go。

11. tryと|?>: 制御効果の脱出境界

try eはResultの成功値を取り出し、失敗なら周囲の関数から早期returnする。コンパイラが保存しなければならないのは「どの関数から脱出するか」である。EscapeResultは既に作られたResultを調べ、EscapeCallはGoの(T,error)を受け取る呼び出しと脱出条件を融合する。どちらもTo *core.Funcで脱出先を表す。

|?>はResultを返すパイプを、合成した局所的な脱出境界の中で評価できる。連続する成功経路は中間Resultを毎回構築せずに融合する。しかし、もともとユーザー関数を脱出先とする明示的なtryを、合成クロージャの内側へ移すとreturnの行き先が変わる。

そこでhasUnguardedTryで局所ラムダに遮られていないtryを検出し、必要ならpipeTryMixedでチェーンを分割する。明示的tryのある部分は元の境界で評価し、安全な連続区間は局所境界内で融合する。制御効果のスコープを保ったまま変換する操作である。

参照: lower/expr.go、pipe-try-segmented-fusion。

12. 末尾再帰と初期化依存グラフ

12.1 Tail position

関数の結果をそのまま返す位置を末尾位置（tail position）という。自己再帰呼び出しがその位置なら、呼び出しをTailCallとしてループへ変換できる。戻ってからさらに演算する位置や、他の引数の計算の内側は同じ変換ができない。ANF化後のCoreを調べることで位置を明確に判断できる。

12.2 @tailrecが要求する保証

@tailrecは単に変換を試みる指示ではなく、変換が成立することを要求する。少なくとも一つの末尾自己再帰があること、許されない非末尾自己再帰がないこと、関数値として自己参照しないこと、相互再帰により保証が崩れないことを検査する。

相互再帰は参照グラフの強連結成分（strongly connected component, SCC）で考えられる。SCCは各頂点から他の頂点に相互に到達可能な集合である。関数・変数の参照関係が循環し、自分だけの成分ではないなら、単一関数の自己再帰をループにするだけでは一般にスタック消費を防げない。CheckTailRecMutualはパッケージ横断でこれを調べる。

12.3 パッケージ初期化循環

Goのトップレベル変数初期化には依存順がある。CheckInitCyclesはCoreの変数・関数の参照関係を調べ、関数本体を経由する参照も含めて変数間の循環を検出する。元のGomの宣言ではなく生成するCoreの宣言形を基礎にするため、実際のGo出力に近い依存を調べられる。

参照: lower/tailrec.go、lower/tail.go、lower/initcycle.go。

13. データ型をGoへ写像する

一般的なGomのADTはGoで閉じたインターフェースとバリアントごとの構造体として表現する。概念的には次のようになる。

type Shape interface { isShape() }
type Shape_Circle struct { Radius float64 }
type Shape_Rect struct { W, H float64 }
func (Shape_Circle) isShape() {}
func (Shape_Rect) isShape() {}

matchはtype switchなどへ変換される。コンストラクタは構造体の生成、分解はフィールドの取得である。Resultは例外的に専用のタグ、成功値、失敗値を持つ表現を使い、SwitchTagで分岐する。Unitはstruct{}、GomのIntはint64に対応し、Goのintとは区別される。

型の論理的同一性と、Goでの物理的表現を混同してはいけない。型の写像はcodegen/types.goにあり、選択した表現に応じてCoreに別のノードが現れる。コード生成が毎回元のGom構文から型表現を選び直すわけではない。

参照: codegen/types.go、codegen/decl.go。

14. Goコード生成: destination passing

14.1 式の結果をどこへ置くか

Goのifやswitch自体は値を返さない。一方Gomには値を返すifやmatchがある。codegen/emit.goは式を出力する際に宛先（destination）を渡す。宛先にはReturn、Assign(name)、Declare(name)、Discard、リスト構築用の宛先がある。

概念的なCore:
  let label = if n > 0 then "pos" else "neg"
  tail = label

概念的なGo:
  var label string
  if n > 0 { label = "pos" } else { label = "neg" }
  return label

各分岐は同じ宛先へ代入し、末尾ならreturnする。不要な一時クロージャを挿入しなくても式指向の意味をGoの文へ変換できる。使われていない中間値でも副作用は実行する。Goは未使用ローカル変数を拒否するので、値が不要な場合には束縛の宣言を省き、評価だけを出力する。

14.2 Go全体をgo/ast.Fileで組み立ててはいない

現行実装の重要な詳細として、Goソースはハイブリッド方式で作る。型や式の一部をgo/astで表しgo/printerで書き出す一方、宣言や制御文の多くはコード生成バッファへ直接テキストとして追加する。最後にcodegen.renderがgo/format.Sourceで整形する。Output.ParseFile()は完成済みの出力をGo ASTへ再解析する補助関数である。

そのため、既存のdocs/design.mdにある「Core IR → go/ast」という説明は、現行のコード生成経路を厳密には表していない。今回の調査記録で文書と実装の差として扱った。

14.3 ソース位置の保持

すべてのCoreノードがdiag.Spanを保持する。出力時には一時的な//gomsrc印を入れ、go/formatの後に//line path.gom:Nへ置換する。この印を利用してSourceMapのアンカーも作る。生成Goのエラーやpanicの位置をGomソースへ対応させるためである。

test宣言と@testヘルパーは_test.goへ分離でき、TestMappingがGom側のテスト名と生成したGoテスト関数名を対応させる。

参照: codegen/codegen.go、codegen/gen.go、codegen/emit.go。

15. 簡単な例を段階別に追跡する

次の例は構造を説明するためのものであり、出力コードとIRの具体的な綴りは実際のダンプで確認する。

package main

type Shape =
  | Circle (radius: Float)
  | Rect (w: Float) (h: Float)

fn area (s: Shape) -> Float = match s {
  Circle r -> 3.14159 * r * r
  Rect w h -> w * h
}
段階 処理の結果
parse TypeDecl、FnDecl、Match、CtorPat、乗算式のAST
resolve Shape、各コンストラクタ、area、s、r/w/hのシンボル束縛
check 対象とパターンの型、各演算と各腕のFloat型を確定
pattern CircleとRectがバリアントを覆うことを確認
lower コンストラクタ別のDSwitch、フィールドの取り出し、腕のDLeafを組み立てる
codegen Goの型宣言、type switch、分岐内の計算とreturnを出力する

この例でcheckは型と呼び出し規約、patternは値の集合に対する被覆、lowerは実行する分岐構造をそれぞれ扱う。三者を同じ「matchの処理」として一括りにしないことが重要である。

16. 実装を読みながら検証する方法

コードを読む際は、まずbuild.Compile / CompileFilesを確認し、次にresolve.Files、check.Files、check.unify、check.Applyの順で追う。その後、静的検査のpattern/matrix.goと実行木生成のlower/pat.goを比較し、lower/expr.goのANF化・呼び出し分類を追って、core.Validate、codegen/emit.goへ進む。

gom dumpにはsyntax、resolve、check、coreの四フェーズがある。

gom dump -phase=syntax main.gom
gom dump -phase=resolve main.gom
gom dump -phase=check main.gom
gom dump -phase=core main.gom
gom check main.gom
gom build main.gom

ダンプはS式風のツリーで、name%Nは同一シンボルを、@start:endはUTF-8のバイト範囲を示す。patternは独立したIRを作るフェーズではないため、専用のdump -phase=patternはない。複数ファイルのパッケージでは、gom dumpも同じディレクトリの兄弟ファイルをコンパイル単位に含める。

変更の検証では、型付きAST・Core・生成Goの差分をそれぞれ見て、Goコンパイルと実行結果による確認を加える。core.Validateの不変条件テストだけで実行意味の一致を保証したとはしない。

理論概念 意味 対応箇所

一般化・具体化 letの型変数の量化と使用時の新しい未知型への置換 check/check.go / check/unify.go
value restriction 多相化を許すletの値の条件 check/check.go
固定点反復 解決が進まなくなるまで保留制約を再訪 check.finalize

決定木 実行用の条件分岐を表す木 lower/pat.go, core.DTree

18. 設計変更時に確認すべきこと

  1. 新しい構文は既存の型付きASTに正しく意味を持たせられるか。そうでなければsyntax・checkで表現を追加する。
  2. 定義の同一性をresolveで固定できるか。受け手の型が必要な参照はcheckで保留すべきか。
  3. 型制約を解くには何が必要か。期待型、デフォルト型、Goとの変換が既存の規則と干渉しないか。
  4. パターンの網羅性と実行用の決定木を別々に定義・検証できるか。
  5. Coreに評価順序、部分適用の実行タイミング、脱出先、Go境界の変換を明示できるか。core.Validateで不正形を検出できるか。
  6. 最後にGo出力を決める。codegenへ新しい意味規則を持ち込まず、Goによる型検査・実行テストまで行う。
