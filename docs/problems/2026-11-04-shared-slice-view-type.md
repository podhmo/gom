# コピーせずに共有するスライス型（View）を足すか

- 状態: 未決（パフォーマンスチューニングに着手するときに再検討する）
- 日付: 2026-11-04

## Situation

`List` はスライスで表現する（P0-3、`type List[A] []A`）ので、`List T` と Go の `[]T` の境界変換は、表現の上ではコピーなしにできる。spec 8.5 は安全のため境界で両方向コピーする。コピーを避ける経路は `Go.Slice T` だけだが、`Go.Slice` には Gom 側の操作がない。

`List`・`Go.Slice` とは別の第三の型として、MoonBit の `StringView` に近い「借りて読むだけのスライス型」（仮に `View a`）を足す案がある。

## 分析

View の安全性は、元のデータの持ち主で決まる。

| 型 | 持ち主 | 書き換え |
| --- | --- | --- |
| `List a` | Gom | 不変 |
| `View a`（案） | 借りているだけ | Gom 側からは読み取り専用。元が Go なら Go 側の変更で中身が変わり得る |
| `Array a` | Gom | 可変 |
| `Go.Slice a` | Go | Go 側で可変 |

- **`List` から作る View**: 元が不変なので安全（`StringView` と同じ状況）。部分の取り出し・添字アクセスが O(1) で、コピーは要らない
- **Go のスライスから作る View**: 書き換えはできないが、Go 側の変更が見える **共有されたスライス**。可変スライスではない。実質、`Go.Slice` に読み取り専用の操作を足したものと同じになる

利点:

- 大きなデータが境界でコピーされない
- cons 構築ループのバッファ化（open-questions「生成コード特殊化ポリシー」、[problems](2026-11-05-stdlib-cons-built-combinators-quadratic.md)）で、受け皿になる型ができる
- `Go.conv` は常にコピーにでき、コピーしない経路は View か `Go.Slice` に任せられる

欠点:

- `map`/`fold` などを型ごとに用意する必要があり、関数が増える。型クラスがないので、共通化するなら辞書渡しか重複になる
- Go 由来の View は、同じ式でも評価した時点によって値が変わる。純粋なコードの中に別名の問題が入り込む。mutable-sharing lint（W0701/W0702、[decision](../decisions/2026-11-04-mutable-sharing-lint.md)）での扱いも決め直しになる

## 当面の方針

新しい型は足さない。`Go.Slice` に読み取り専用の操作を足し、`Go.conv` はコピーありに揃える（[decision](../decisions/2026-11-04-goconv-list-slice-copies.md)）。`List` 由来の安全な View は、パフォーマンスチューニングで必要になったらこのファイルから再検討する。
