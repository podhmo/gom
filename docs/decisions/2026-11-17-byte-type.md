# `byte`/`uint8` → `Byte` を組み込み型として公開する

- 状態: draft
- 日付: 2026-11-17

## 背景

`os.ReadFile`、`io.ReadAll`、`json.Marshal`、`utf8.Valid` など byte I/O の
中核 API が `[]byte` を返し・受け取るが、要素の `byte`/`uint8` は v1 で
未対応型として公開面から外れていたため、これらのシンボルはすべて E0501 で
隠れ、Gist CLI は example-local の host adapter で代替していた
（[prototype](../sketch/2026-11-03-gist-cli-prototype.md)）。

## 決定

`Byte` を組み込み型として追加し、Go の `byte`（`uint8`）に対応させる。
`[]byte` はシグネチャ境界の既存の `[]T` 規則に従い `List Byte`、
入れ子位置では `Go.Slice Byte` と読む — 新しい変換規則は増やさない。
`Go.conv data : String` / `Go.conv s : Go.Slice Byte` は go/types の
変換規則（`string([]byte)`、`[]byte(s)`）にそのまま従う。

`Byte` の操作は I/O に必要な最小限だけ:

- `==`/`!=`（Go の byte と同じ等価比較）
- `Go.conv` による数値型との相互変換（`Go.conv b : Int`、`Go.conv n : Byte`
  は 0–255 の範囲判定 — `litRange` は unsigned 8 ビット）
- `List Byte`/`Go.Slice Byte` の既存の操作面（`List.*`、`Go.Slice.*`）

リテラル、四則演算、`<` 系の順序比較は持たない。必要になれば `Go.conv` で
`Int` に変換するか、別 decision で演算を足す。

## エイリアス問題への位置づけ

`rune`/`Char` の対応と同じく、`byte` は `uint8` の別名なので「別の Gom 型」への
写像は型レベルでは区別できない — `uint8` と `byte` はどちらも `Byte` に読まれる
（[problems](../problems/2026-11-06-rune-char-correspondence.md) が記録した懸念は
構造的に残る）。`rune` → `Int32` は int32 API との混同を避ける選択だったが、
`byte` には対になる表記がないため、`byte` 側に素直な名前 `Byte` を採った。

## 影響

- spec §3.1/§8.3 に `Byte` を明記し、§8.3 の未対応リストから `byte`/`uint8` を外す
- `[]byte` を含む Go シンボル（`os.ReadFile`、`io.ReadAll`、`json.Marshal`、
  `utf8.Valid`、`io.Copy` 等）が公開される
- gist-cli の byte I/O / 引数 / JSON-quote adapter が Gom に移る。
  `StringField`（書き込み先 decode）と `NewClient`（struct 構築+callback）は
  別の未決定面なので adapter に残す
