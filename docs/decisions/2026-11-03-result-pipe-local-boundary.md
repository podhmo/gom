# Result パイプの局所的な制御フロー

- 状態: 採用
- 日付: 2026-11-03
- Supersedes: [try-boundary](2026-11-01-try-boundary.md) のうち `|?>` が利用者の関数から脱出するという Core IR 上の解釈

## 背景

spec 9.2 の `|?>` は Result.bind であり、失敗は式の値である。既存 lower は利用者の関数を EscapeResult/EscapeCall の宛先にしていたため、パイプ外の処理まで中断し、トップレベルや Unit 関数では不正な IR を生成していた。評価器は値としての意味を実装している。

## 案

通常のパイプチェーン全体に、lower が作る即時適用の Unit 引数クロージャを一つ置く。連続する左辺チェーンは同じ局所境界で payload を受け渡し、Go の `(T,error)` 呼び出しは EscapeCall に融合する。利用者の関数は脱出しない。最終段だけ Result を構築する。

明示的な `try` を含むパイプは決定木の Ok/Err 分岐として lower する。利用者の式を合成クロージャへ移さず、try の関数境界を保存する。エラーラップだけは既存 EscapeResult の局所クロージャを用い、意味を codegen に追加しない。保守的な判定でラムダ内の try もこの経路を使う。

## 追加の実装判断

- 数値・順序制約の付いた未解決型は Result ではないので、パイプ先頭では Result への単一化を試さない。数値から始まるパイプも spec 9.2.7 を満たす。
- エラーラップ用の format string ではステップ名中の `%` を `%%` にする。ファイル名を含む名前でもそのまま表示し、常に `%w` だけを書式指定子にする。
- 評価器には任意の `diag.LineIndex` を渡せる。無名ステップを実ソースの行番号で表示し、ソースのない手書き AST のみ既存のバイトオフセット fallback を維持する。
