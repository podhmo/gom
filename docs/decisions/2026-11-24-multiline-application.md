# 複数行のカリー適用 — NL-2 は変えず、`|>` か `( )` で括る

- 状態: 採用（wave44 lane G で調査・採択）
- 日付: 2026-11-24

## 決定

改行ルール（NL-2: `prev` が式を終われ、`next` が line-start
でなければ NL を挿入）は変えない。複数行にまたぐ関数適用は
次のいずれかで書く。

1. 引数が最後に来る向きにカリーされていれば `|>` パイプライン
   （`|`>` は line-start なので行頭に置けば継続する）:

   ```gom
   let r =
     [1, 2, 3]
     |> List.fold (fn acc x -> acc + x) 0
   ```

2. それができない場合は適用全体を `( )` で括る。NL-1 により
   括弧内の改行はただの空白になる:

   ```gom
   let r = (List.fold
     (fn acc x -> acc + x)
     0
     [1, 2, 3])
   ```

## 理由

候補は「`(`（と `[`）を line-start に加えて、次行が `(`/`[`
で始まれば適用を継続する」「文法を変えず慣例として扱う」の
2 つだった。

`(` を line-start にすると既存の正当なプログラムが壊れる:

```gom
fn main () -> Unit = {
  f ()
  ()          // Unit ブロックの標準的な終端
}
```

`f ()` は `)` で終わり（can-end）、次行が `(` なので NL が
消え、`f () ()` — `f ()` の戻り値への適用 — に読み替わり、
`f ()` が `Unit` を返すなら E0401 になる。`()` を末尾に置く
ブロックは testdata だけでも 110 箇所（直前が `{` の 1 件を除く
109 件が実際に破壊対象）あり、標準イディオムを
大量に壊す。`[` も同じで、`expr` の次行に置いたリスト
リテラル（ブロックの値として一般的）が `expr` の引数化する。

破壊的でない変種（インデントを見る等）は「インデントは意味を
持たない」という言語の基本原理（spec 1.5 節）と衝突し、
新たな文脈依存をレクサに持ち込む。書き味の利得に対して
一貫性の代償が大きすぎるため、文法変更は却下する。

なお `(fn ...)` など括られた引数の後に続けて引数を改行しても
分断される — 継続するのは次行が二項演算子（`|>`、`<|`、`+`
など）、`else`、または裸の `|` で始まる場合だけで（`|` は
variant 宣言の継続行に使う規則）、`arg\n arg2` のような
「引数行」は別の式になる。

## 検証

`testdata` 内の `()` 終端ブロック行が 110 箇所あることを
確認し、上記 2 つの慣例と失敗形（診断の種類はブロック内では
分離行が末尾なら結果型チェックの E0401 / それ以外は E0402/E0407、
ファイルスコープでは E0101）を `testdata/gocall`
配下の仮ファイルで確認した（[検証レポート](
