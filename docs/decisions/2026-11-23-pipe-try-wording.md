# `|?>` 自動ラップの文言カスタマイズ

- 状態: draft
- 日付: 2026-11-23
- 問い: `|?>` が付ける `ステップ名: メッセージ` の文言を設定可能に
  するか — open-questions の残る未決（wave33 lane D の調査）

## 現状

- ステップ名は右辺先頭の名前そのまま（`os.ReadFile`、
  `parse_with opts` → `parse_with`、無名なら `file:line`）— 
  `lower.stepName`
- フレームは `*rt.StepError{Step, Err}`。`Step` が構造化データ
  として既に外部から読めるので、文言を変えたい消費側は
  `errors.As` で取り出して再描画できる
- 自分で文言を制御したい経路は既にある:
  `rt.StepErr`（`import go "github.com/podhmo/gom/rt"`）を
  `Result.map_err` 経由で自前のフレームを付けるか、
  `try` + `match` で素の Result を扱う
- wrap は GoError のときだけで、二重名（`strconv.Atoi:` の
  重複）は容認の方針が採用済み

## 選択肢

### 案 A: ステップごとの文言構文（棄却候補）

`|?> "msg" step` のような per-step 文言。文字列リテラルが右辺
先頭に来る形は現行では型エラーなので文法的には割り込めるが、
`"msg" f` が「文言注釈」になるのは言語臭いし、`step "msg"` は
通常適用と衝突する。専用構文か属性記法（`|?> step ~as:"msg"`）
を新設する必要があり、文法面を割くほどの要求頻度は見込めない。

### 案 B: ファイル/パッケージ単位の書式指定（保留候補）

`//gom:stepfmt "<fmt>"` のようなディレクティブで書式を与える
（`{step}` `{file}` `{line}` 等のプレースホルダ）。文法変更なし、
`//gom:` ディレクティブの既存枠組み（wave33 lane B で fmt 対応も
済）に乗る。ただし一律書式はステップ識別性を薄めやすく、
`{step}` を必須にすると結局「接頭辞を変えられる」だけの機能に
なる。需要が出た時点で実装するのがよい。

### 案 C: 現状維持 + 回避経路の文書化（採択候補）

カスタマイズ需要は「エラーを人間向けに整形する」最終段の関心
で、`Step` フィールド + `map_err` + `try`/`match` で達成可能。
文言のデフォルトは一貫しているほうが読みやすい。open-questions
の項目を「不要になったら消す」扱いにし、spec 9.2.8 あたりに
回避経路（`rt.step_err` 自作ラップ）を1行足す。

## 制限・補足

- 案 B を将来採用する場合、fmt の `//gom:` 保護が済んでいるので
  ディレクティブ消失の懸念はない
- `try`（`|`?>` なし）は wrap しない現行動作に触れない
