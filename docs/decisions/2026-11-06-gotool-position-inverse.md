# Go-position inverse: anchor-table candidate enumeration and the ambiguity fallback

- 状態: 採用（実装・検証した — [検証](../sketch/2026-11-06-gotool-inverse-verification.md)）
- 日付: 2026-11-06
- Supersedes: none — completes the deferred half of [source-location-correspondence](2026-11-03-source-location-correspondence.md) ("a SourceMap-aware reverse lookup ... is a design input for P4-6")

## Context

`build.GoPosIndex.Resolve` restores a printed `file:line:col:` the
way Go reports it: `line` is taken as a `.gom` line number verbatim.
That is wrong wherever `//line` drift ran past a construct's real
extent — a generated line deep inside a multi-line expansion reports
a `.gom` line number a *different, real* line also claims (the
aliasing the gaps ledger records). Two shapes matter:

- `_ = result.FromGo(...)`-style synthesized statements emit **no**
  sentinel of their own, so they report the line following their
  construct's `.gom` line — colliding with the next `.gom` line's
  own anchors.
- Every unanchored generated line (`}` closers, blanks, the
  `//line` directive lines themselves) also drifts; most can never
  carry a diagnostic, but a `}` can (`missing return`).

`diag.SourceMap` already records the per-directive anchors
(`Anchor{Line, Span}`), derived from the same splice that writes the
`//line` directives. What was missing is the inverse of the mapping
the toolchain applies: reported `.gom` line → generated line(s) that
produce it → the construct span anchored there.

## Decision

### The inverse is candidate enumeration, not line arithmetic

`SourceMap` gains two additive lookups:

- `ReportedLine(gen, li)` — the forward direction: which `.gom`
  line generated line `gen` prints under this file's `//line`
  directives (the governing anchor's pinned line plus the distance
  into its region). Exists mainly so the inverse is testable by
  round-trip and so callers can ask "what does line g claim".
- `Candidates(reported, li)` — every `(generated line, anchor)`
  pair whose `//line` numbering prints `reported`. A reported line
  names a generated line `g` under anchor `a` when
  `g = a.Line + reported - pinnedLine(a)` falls inside a's region
  (`[a.Line, next.Line)` — the region *includes* the next
  directive's own line, which still reports under the old
  numbering). Each match is flagged `Drifted` when `reported` runs
  past the anchor span's own `.gom` line extent.

### Generated lines that cannot carry a diagnostic are not candidates

The ambiguity set is much smaller than the raw enumeration because
most drift lines are blanks, `//line` directives, or comment-only
lines — lines the toolchain never reports on. `GoPosIndex` keeps
the generated bytes next to each registered map
(`AddSourceMap(path, genSrc, map)` — one call per generated file,
so `Output.Source`/`TestSource` register independently) and drops
candidates whose generated line is empty or comment-only. `}` and
other closer lines stay — `go build` does report on them.

### The answer is exact, drift, or ambiguous — never a silent alias

`GoPosIndex.ResolveMatch(file, line, col)` classifies:

- **exact**: one distinct construct span claims the report
  on-station (`reported` inside the span's `.gom` lines). The span
  is the construct's fragment on the reported line — tighter than
  the whole construct, honest to what the report asserts. Same
  span anchored several times (re-anchored sub-statements) dedupes
  to one candidate, not an ambiguity.
- **drift**: one construct, but `reported` runs past its extent —
  the true position is somewhere inside the construct, so the
  answer is the construct's whole span and `Kind` marks drift.
- **ambiguous**: several distinct spans claim the report (a drifted
  code line colliding with a real line, same-line siblings, or the
  main/test maps both claiming it). The answer is the union of the
  candidate spans — never confidently wrong — and `Candidates`
  carries every contender. Preferring the on-station reading was
  rejected: the drifted reading is exactly as plausible and picking
  it silently is the aliasing bug with extra steps.

`ResolveMatch` is the match-aware lookup; `Resolve` keeps the
naive point-mapping contract for callers that only hold a reported
line. `GoToolDiagnostics`, `ResolveStack` and `RenderStack` move
to the match (drifted stack frames render their construct's line
instead of a real-but-wrong one; ambiguous frames keep the printed
line — the printed claim — but drop the PC-offset trailer, so the
two-part panic shape still marks them as mapped). Without
registered maps every result degrades to today's naive answer, so
map-less callers are unaffected.

`GoToolDiagnostics` folds through the match: drift sets
`data["drifted"]`, ambiguity sets `data["ambiguous"]` plus the
candidate spans — open-ended `data` carries what the message format
does not enumerate (spec section 12, item 3).

### Live fold: `gom test` build output; `go vet` stays unwired

`gom test`'s build-output events are the go-build diagnostics of
the package (its compile step *is* `go build` over the package plus
test files). `runGoTests` registers each input's `SourceMap` and
`TestSourceMap` on its `GoPosIndex`, upgrading the existing
`GoToolDiagnostics` fold with no new process invocation — zero
added session cost.

`go vet` still has no live caller: a vet pass needs its own
spec-surface decision (which command pays the extra tool run), and
the LSP consumption surface needs a bigger one — `gom lsp` compiles
CheckOnly today (no codegen → no SourceMap) and has no scratch
package dir a go tool could check. The substrate built here is the
prerequisite either way; the ledger entries are narrowed, not
closed.

### Cheapest emission change for a fully unambiguous inverse — recorded, not taken

If ambiguity itself must die, the honest emission fix is **a re-pin
directive per generated code line inside a construct's region**
(each continuation line re-anchored to its own construct's `.gom`
line): no report ever aliases, at the cost of roughly doubling
`//line` count inside multi-line expansions and hurting generated
readability. Alternatives considered and rejected: encoding the
anchor index in the `//line` filename operand (changes
user-visible positions — spec surface) and a sidecar anchor-table
artifact (the ambiguity lives in the printed position, not in a
missing table — a sidecar cannot recover which generated line was
meant). Both the build-side fallback above and the emission change
remain possible; codegen emission is another lane's surface this
wave, so this decision takes the build-side inverse and records the
emission option for it.

## Consequences

- `internal/diag/srcmap.go`: `ReportedLine`, `Candidates`,
  `AnchorMatch` — additive.
- `internal/build/gopos.go`: `AddSourceMap`, `ResolveMatch`,
  `PosMatch{Span, Kind, Mapped, Candidates}`, kinds
  `MatchExact`/`MatchDrift`/`MatchAmbiguous`; `GoToolDiagnostics`
  marks `drifted`/`ambiguous`; `RenderStack`/`ResolveStack` are
  match-aware.
- `cmd/gom/test.go`: the per-directory index registers outputs'
  maps — the fold is live through `go test` build-fail events.
- A diagnostic on a drifted line lands on its real construct
  instead of a wrong-but-real `.gom` line; an ambiguous one squints
  at the union and says so in `data` instead of lying with a point.
- Residual: the union/`ambiguous` shape stays until codegen emits
  the per-line re-pin (recorded above); `SpanAt`'s inner-span
  granularity is unchanged and still answers editor queries.

## Verification

Verified — see
[docs/sketch/2026-11-06-gotool-inverse-verification.md](../sketch/2026-11-06-gotool-inverse-verification.md).
A real `go build` on tampered generated output reports
`./main.gom:8: missing return` (drifted `}` → the construct's span,
`data["drifted"]`) and `./main.gom:14: undefined: nope` (a drifted
materialization line colliding with the real line-14 construct →
the honest union, `data["ambiguous"]` + `data["candidates"]`).
Cost: ~55–60ms per cold single-package `go build`; zero added
invocations for the live `gom test` fold. The LSP invocation site
is deferred — `gom lsp` compiles CheckOnly today, so the go-tool
run has nothing to check (the sketch records the wall precisely).
