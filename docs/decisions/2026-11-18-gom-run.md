# `gom run` サブコマンド: go build + temp バイナリ実行

- 状態: 採択
- 日付: 2026-11-18

## 状況

`go run` 相当の実行経路がなかった — `gom build` → 手動 `go run`/`go build` の 2 段構え（wave18 lane4 で open-questions へ移管し、wave19 lane2 で採択された課題）。

## 決定

`gom run [-format F] [FILE|DIR ...] [-- ARGS]` を新設する。

- **生成物の置き場**: `gom build`/`gom test` と同じ — 生成 `.go` をソースの隣に書く。temp dir への書き出し案は、生成コードが `github.com/podhmo/gom/rt`・`stdlib/*` をユーザーの module 経由で解決する以上、module 外の dir では `go build` 自体が成り立たない（go.mod を仮組みしてもユーザー側の別 Gom パッケージ import が解決できない）。module 内に置く既存モデルをそのまま使う
- **リンク**: `go build -o <temp dir>/out`（internal/build の `RunGoRunBin`）。`go run` を使わない — 子プロセスの失敗をすべて `exit status 1` に潰し stderr に余計な行を混ぜるため。直接起動すれば終了コード・stdout・stderr が素通しする
- **実行**: temp バイナリを `--` 以降の引数で起動。stdin は呼び出し元の端末、workdir は呼び出し元のカレントディレクトリ（`go run ./pkg` と同じ）。終了コードは子プロセスのものをそのまま返す
- **制約**: 入力は単一のパッケージディレクトリで、生成物に `package main` を含むこと。`go run` と同じ制限であり、複数ディレクトリ・非 main は使用エラー（2）
- **診断の畳み**: コンパイル失敗・`go build` 失敗は通常のメッセージストリーム（`GoToolDiagnostics` 経由で `.gom` 位置へ）を出す。成功時は `summary` も出さない — stdout はプログラムのものだけ、という `go run` の契約
- **ビルドキャッシュ**: 使わない — リンク段にコンパイル出力が必要で、cache hit は出力を供給しない（`gom build -go`/`-vet` と同じ opt-out）
