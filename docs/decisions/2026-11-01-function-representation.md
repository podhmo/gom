# 関数値の表現

- 状態: 採用（P0-2 の実験で決定。根拠: [sketch: P0-2](../sketch/2026-11-01-p0-2-function-representation.md)）
- 日付: 2026-11-01
- Supersedes: [juxtaposition-and-currying](2026-11-01-juxtaposition-and-currying.md) のうち関数値の表現（`func(A) func(B) C` のカリー化形で持つ）

## 決まったこと

- 多相な定義と、実行時の関数値を IR 上で区別する。多相な定義を値として使う箇所で型引数を具体化し、そのあとで arity を調整して Go の関数やクロージャにする

```
多相な定義 ─(型引数の具体化)→ 単相の関数値 ─(arity の調整)→ Go の関数 / クロージャ
```

- 既知の関数への引数が揃った呼び出しは、Go の多引数呼び出しに直接変換する（[juxtaposition-and-currying](2026-11-01-juxtaposition-and-currying.md) のとおり）

## P0 で決めたこと（P0-2）

- 関数値は arity 付きの形で持つ。Gom の型 `T1 -> ... -> Tn -> R` の値は Go の `func(T1, ..., Tn) R`（矢印チェーンを平坦化した形が canonical）
- 定義 `fn f (a1)...(am) = e` は宣言どおりの arity の Go 関数 `func f(A1,...,Am) R'` にする（外側の本体が外側の呼び出しで評価される順序を保つため）。`R'` 自身も平坦化した func 型になりうる。宣言 arity をまたいだ平坦化はしない
- 値として使うとき: 宣言 arity = 型の矢印長ならそのまま参照する。宣言 arity が小さい（関数を返す関数、`fn mk_add (a) -> (Int -> Int)` 型）場合だけ平坦化ラッパーを生成する
- 呼び出しは既知・未知を問わず、残りの arity ぶんの引数で 1 回の Go 呼び出しにする。部分適用は残り arity のクロージャを呼び出し側に生成する（多相な定義の具体化の時点は値として使う箇所——上の「決まったこと」のとおり、両方式で同じ）
- カリー化形 `func(A) func(B) C` は不採用。実測で、境界を越えた関数値の適用に n-1 個の中間クロージャ割り当て（arity 3 で ~43 倍）、高階関数のループ内で要素ごとの割り当て（fold で ~87 倍）、Go API への受け渡しに Uncurry アダプタが必要（`slices.SortFunc` で ~12 倍）だった。公開面も `func(T1) func(T2) R` は非慣用的で、flat 形を直接受け取る特殊化版の用意も、curried 値を `UncurryN` しても per-call のチェーンコストは消えない
- ラベル付き引数の部分適用: ラベルが宣言順とずれる呼び出し側で並べ替えクロージャを作り、本体は常に宣言形（フラット）を呼ぶ。ラベルは消去され Go の引数は宣言順
- `CurryN` / `UncurryN` アダプタは、curried な形を取る珍しい Go API のためだけに用意する（調べた標準ライブラリのパターンでは不要だった）
- パッケージをまたぐ関数値の公開形は `func(T1, ..., Tn) R`。Go 側は素の Go 関数をそのまま渡せ、逆に Gom の関数値も `slices.SortFunc` などへ直接渡せる
