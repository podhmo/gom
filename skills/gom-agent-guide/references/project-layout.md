# Project layout and commands

Two contexts: **a user's Gom project** (one dir = one package over a
Go module) and **this compiler repo** (where the language itself is
implemented and dogfooded).

## A Gom project

```text
mypkg/
  go.mod          # ordinary Go module; generated .go resolves here
  main.gom        # package main, fn main () -> Unit
  shapes.gom      # more files of the same package
  shapes.gomi     # the package's interface (library pkgs: required)
  main.go         # generated by `gom build` — do not hand-edit
```

- `gom build main.gom && go run .` — Gom emits `.go` next to the
  source; the module's `go.mod` must reach `github.com/podhmo/gom`
  for the `rt`/`stdlib` imports in generated code (see how each
  `tutorial/NN/` does it with a `replace` line).
- Dependencies on Go packages need nothing extra — `import go
  "path"` resolves through the module's normal `go list`.

## Commands

| Command | Meaning |
| --- | --- |
| `gom check FILE|DIR ...` | parse → resolve → check → pattern; JSON-Lines diagnostics. `DIR` expands to its `*.gom`/`*.gomi`. |
| `gom build [-o OUT] FILE|DIR ...` | + lower → codegen; writes `.go`. `-o` file (single input) or dir. |
| `gom dump -phase=NAME FILE` | `syntax`/`resolve`/`check`/`core` IR tree → stdout; diagnostics → stderr. The package's sibling `.gom` files compile along so member names resolve — only FILE's IR prints. |
| `gom fmt [-w\|-d\|-l\|--check] FILE...` | canonical formatter; `-` = stdin→stdout. Streams go to stderr. |
| `gom test FILE|DIR ... [-- FLAGS]` | compiles in test mode, writes `.go` + `_test.go` beside each input, runs `go test -json` per package directory, reports one `test` message per test plus `summary.tests` counts. FLAGS after `--` pass verbatim to `go test` (`-race`, `-run`); `-q`/`--quiet` drops the raw half of panic stacks. Library packages need their `<pkg>.gomi` — the conformance gate runs here too. |
| `gom fix FILE...` | applies the fixes diagnostics mark `safe`. |
| `gom explain [CODE]` | error-code explanation(s). |
| `gom schema` | JSON Schema of the message stream. |
| `-format text` | human diagnostics instead of JSON on all the above. |

`gomi` was renamed `info` — `gom gomi` prints the pointer and exits
2. Everything in the table above is implemented.

## Running the tutorial

```sh
cd tutorial/01-hello && gom build main.gom && go run .
tutorial/run.sh          # build + run + diff every chapter
go test ./tutorial/      # same drive as a Go test
```

`tutorial/10-errors/badmatch.gom` is intentionally broken — the only
chapter that fails `gom check` (E0301 demo).

## Repo checks (compiler development)

`make check` = gofmt + `go vet` + `go test -race` + sumtype +
staticcheck + experiments. The contract for any change:

```sh
gofmt -l .        # must print nothing
go vet ./...      # clean
go test ./...     # green
```

Test suites: `go test ./internal/build` drives `testdata/spec` and
`testdata/golden` (TestSpec/TestGolden in `harness_test.go`;
`-update` rewrites expectations, e.g.
`go test ./internal/build -run 'Spec|Golden' -update` —
`internal/gomtest` is the harness library, not the driver); the
skill's own examples are verified by `go test ./skills` — every
`gom` fenced code block in these docs is compiled with `gom check`
semantics (`fail[=CODE]` asserts a diagnostic, `skip` opts out,
`gomi` checks an interface file).
